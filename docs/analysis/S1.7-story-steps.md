Story S1.7 Implementation Steps:

Step 1. Enable scheduled execution through the platform's sanctioned cron entry point
Must Support:
- Scheduled jobs reach the platform core through the sanctioned entry point the core itself provides and documents for cron-driven processing
- Each scheduled occurrence executes exactly once — no duplicated and no missed runs
Manual Verification:
- Trigger a scheduled interval and confirm the execution record shows it ran through the core's sanctioned cron entry point
- Confirm the run appears exactly once and its outcome is visible in the execution output
Prerequisite: None
Developer Notes:
- Prefer the entry point the platform itself documents for cron-driven scheduled processing; for the pinned Elgg 2.3.17 core that is the core's HTTP cron endpoint (the wget crontab already wired in S1.2) — when a later core version in the sequence ships its own command-line entry point, move the invocation to it at that upgrade step and re-verify the syntax
- Ensure the service identity that runs scheduled jobs has the access the core expects
- Focus on a single sanctioned execution path rather than parallel mechanisms

Step 2. Enable all platform-supported recurring intervals on the schedule
Must Support:
- Every recurring interval the current platform version supports is scheduled at its defined frequency
- The full schedule set is recorded in version-controlled configuration, reproducible across environments
- The schedule set can be re-verified and adjusted whenever the platform version in the sequence changes
Manual Verification:
- List the configured schedule and compare it against the intervals the current platform version supports — every one is present
- Observe each interval fire at its scheduled time and record an execution outcome
Prerequisite: Step 1 (scheduled execution reaches the core through the core's sanctioned cron entry point)
Developer Notes:
- Derive the interval list from the current platform version's own documentation, not from the previous version's list
- Keep schedules in committed configuration so each upgrade step can re-check them
- Surface failures visibly so a silently missed run cannot go unnoticed

Step 3. Enable end-to-end verification of the periodic data-cleanup task
Must Support:
- The maintenance task that removes stale/expired data runs on its scheduled interval and completes its cleanup work
- Execution produces observable evidence of start, completion, and what was cleaned
- A user can confirm the cleanup effect itself, not merely that the job was triggered
Manual Verification:
- Ensure data exists that the cleanup task targets, let the scheduled run occur, and confirm the execution record shows start and completion
- Confirm the targeted stale/expired data is actually gone afterwards
Prerequisite: Step 2 (the task's interval is scheduled)
Developer Notes:
- Verify with real data in a representative state rather than an empty system
- If early runs find nothing to clean, seed suitable data so the effect is observable
- Record the observed outcome so the verification can be repeated after each upgrade step

Step 4. Enable end-to-end verification of the account-validation notification task
Must Support:
- The task that manages pending account validations performs its notification work through the trigger path the pinned core actually provides: on Elgg 2.3.17 the uservalidationbyemail plugin registers no cron handler — the validation email is sent at registration (uservalidationbyemail_disable_new_user) and re-sent when an unvalidated account attempts to log in (uservalidationbyemail_check_manual_login), both via uservalidationbyemail_request_validation() and notify_user()
- Execution produces observable evidence of the send and its outcome
- A user can confirm the notification effect itself, not merely that the trigger fired
Manual Verification:
- Ensure at least one account is in the pending-validation state (register a fresh account with the plugin active), trigger the plugin's notification path, and confirm the send is recorded
- Confirm the pending account received the validation email, observable in the environment's captured outgoing mail
Prerequisite: Step 2 (the schedule set is committed and re-verifiable; on 2.3.17 this task is not cron-driven — see Must Support)
Developer Notes:
- The development environment captures outgoing messages for inspection — use that to observe the notification effect
- Seed a pending account if none exists so the effect is observable
- Per-upgrade duty: at each upgrade step, re-check whether the core's uservalidationbyemail gains cron-driven expiry notifications/reminders; when it does, schedule the new interval, move this verification to the scheduled run, and re-verify (same discipline as the crontab's per-upgrade duty)
- Record the observed outcome so the verification can be repeated after each upgrade step

Step 5. Enable automatic rotation of the scheduled-task output log
Must Support:
- The scheduled-task output log rotates automatically at its configured size or schedule, without operator intervention
- Rotated archives are retained for a defined period and then removed
- The logging duty formerly covered by the dropped legacy log-rotation plugin is preserved by this configuration
Manual Verification:
- Generate enough scheduled-task output to pass a rotation point and confirm a rotated archive appears
- Confirm the active log continues writing after rotation and that archives beyond the retention window are removed
Prerequisite: Step 2 (scheduled intervals produce recurring output to rotate)
Developer Notes:
- Define retention so diagnostics remain available for troubleshooting across several runs
- Keep the rotation configuration committed alongside the schedule definitions
- This closes the duty left open by the dropped legacy log-rotation plugin
