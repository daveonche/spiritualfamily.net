# Story S1.8 Implementation Steps

Step 1. Enable per-environment application logging configuration
Must Support:

- The application's log verbosity and destinations are configurable per environment (development vs production) without code changes
- Per-environment values are supplied through the committed environment-variable mechanism, never hard-coded
- Deprecation notices are surfaced visibly in the log so upcoming breakage at the next platform version is signaled
Manual Verification:
- Switch the environment configuration between development and production values and confirm the log verbosity changes accordingly
- Trigger a condition that produces a deprecation notice and confirm it appears in the log
Prerequisite: None
Developer Notes:
- Keep per-environment differences in committed, documented configuration so each upgrade step can re-check them
- Surface deprecation notices prominently — they are the early-warning signal for the next major-version move

Step 2. Enable registered error and exception handlers
Must Support:

- Uncaught errors and exceptions are captured into the application log through handlers registered via the platform's sanctioned mechanism
- Handler output follows the per-environment logging configuration from Step 1
- Each captured event produces observable evidence in the log (message, severity, source)
Manual Verification:
- Trigger a deliberate error and an uncaught exception in each environment and confirm both appear in the log with the expected detail
- Confirm production logging does not expose more internal detail than intended
Prerequisite: Step 1 (per-environment logging configuration exists for the handlers to follow)
Developer Notes:
- Register handlers through the mechanism the platform itself documents rather than ad-hoc output paths
- Verify in both the development and production shapes, since verbosity differs between them

Step 3. Verify the committed environment-variable template coverage
Must Support:

- Every variable required by the application's settings file and the container orchestration is present in the committed template with placeholder values
- Each variable's purpose is documented alongside its placeholder
- No real secrets are committed
Manual Verification:
- Compare the template against every variable the settings file and orchestration definitions read and confirm none is missing
- Confirm the committed template contains placeholders only, with no real credentials
Prerequisite: None
Developer Notes:
- Prior work already satisfies this criterion; this step verifies and locks it so later steps build on a complete inventory
- Any variable introduced by later steps must be added to the template in the same change

Step 4. Enable documented secrets-handling rules
Must Support:

- Documented rules state that secrets are injected only through the container orchestration's environment mechanism and the deployment platform's environment settings
- The rules cover what must never be committed and where secrets live in development versus production
- The rules are discoverable from the repository's documentation
Manual Verification:
- Locate the secrets-handling documentation from the repository docs and confirm it states the injection-only rule
- Confirm no real secrets appear in committed files, per the rules
Prerequisite: Step 3 (the template inventory defines which variables are secrets)
Developer Notes:
- Keep the rules short and prescriptive so future upgrade steps can follow them mechanically
- Cross-check the rules against the existing secret-hygiene guard checks so documentation and enforcement agree

Step 5. Enable container log routing to stdout and log files
Must Support:

- Each container service (application, database, scheduled-task runner) routes its output to stdout and/or dedicated log files
- Logs are observable in both the development and production environments
- Application-written log files land on persistent storage so they survive restarts
Manual Verification:
- Exercise each service and confirm its output is visible through the container runtime's log view and/or the dedicated log files
- Restart a service and confirm file-based logs persist
Prerequisite: None
Developer Notes:
- Keep routing definitions committed so each upgrade step can re-verify them
- Align the application's file-log destinations from Step 1 with the persistent storage locations defined here

Step 6. Enable defined rotation for the routed logs
Must Support:

- Rotation is defined for the routed container and application logs and happens automatically at its configured size or schedule, without operator intervention
- Rotated archives are retained for a defined period and then removed
- The rotation duty complements the scheduled-task log rotation already in place from S1.7
Manual Verification:
- Generate enough output to pass a rotation point and confirm a rotated archive appears
- Confirm the active log continues writing after rotation and that archives beyond the retention window are removed
Prerequisite: Step 5 (logs must be routed before rotation can be defined)
Developer Notes:
- Define retention so diagnostics remain available across several runs
- Keep the rotation configuration committed alongside the routing definitions
- Align retention with the window used by the S1.7 scheduled-task rotation for a consistent diagnostics trail
