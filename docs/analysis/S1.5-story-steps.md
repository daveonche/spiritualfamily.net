Story S1.5 Implementation Steps:

Step 1. Enable automated pipeline execution on repository changes
Must Support:
- The pipeline starts automatically whenever changes are pushed or proposed for review
- All checks execute on the single pinned runtime version recorded in the baseline documentation
Manual Verification:
- Push a small change (or trigger a manual run) and confirm the pipeline starts by itself
- Observe the run reports an overall pass/fail status visible to the developer
Prerequisite: None
Developer Notes:
- Keep the pipeline definition committed and versioned alongside the code it validates
- Prefer one pipeline that runs all checks, so a single run gives a complete verdict

Step 2. Enable dependency manifest validation
Must Support:
- A check that validates the dependency manifest's structure and declared metadata
- A failed validation marks the whole pipeline failed
Manual Verification:
- Run the pipeline on the current manifest and confirm the validation check passes
- Temporarily break the manifest on a throwaway branch and confirm the check fails, then restore it
Prerequisite: Step 1
Developer Notes:
- Keep this check independent of installation so manifest problems surface before anything is downloaded
- Validation should be fast, giving the earliest possible feedback

Step 3. Enable reproducible dependency installation from the committed lock file
Must Support:
- Installation that uses exactly the versions recorded in the committed lock file, with no re-resolution
- A missing or unusable lock file fails the check
Manual Verification:
- Run the pipeline on a clean checkout and confirm installation completes using only the lock file
- Observe the run log shows no version re-resolution or substitution
Prerequisite: Step 1
Developer Notes:
- Installation must never silently fall back to resolving fresh versions
- A clean-checkout install proves the lock file alone is sufficient to rebuild the dependency set

Step 4. Enable codebase-wide syntax linting
Must Support:
- A check that scans the project's source files for syntax errors
- Any syntax error fails the pipeline
Manual Verification:
- Run the pipeline and confirm the lint check passes on the current codebase
- Introduce a deliberate syntax error on a throwaway branch and confirm the check fails, then remove it
Prerequisite: Step 1
Developer Notes:
- Scope the scan to the project's own source, excluding vendored third-party code
- Lint output should identify the offending file so fixes are quick

Step 5. Enforce manifest ↔ lock file consistency
Must Support:
- A check that detects divergence between the manifest and the lock file
- Any divergence fails the pipeline rather than producing a warning
Manual Verification:
- Modify the manifest without updating the lock file on a throwaway branch and confirm the pipeline fails
- Restore consistency and confirm the pipeline returns to green
Prerequisite: Steps 2 and 3
Developer Notes:
- Consistency enforcement protects the reproducibility guarantee the lock file establishes
- The failure should point at the mismatched pair so the fix is obvious

Step 6. Enable container image build validation with version build arguments
Must Support:
- The pipeline builds the application image from the committed build recipe
- The build receives the version build argument using the same parameterization as the local orchestration
- A failed image build fails the pipeline
Manual Verification:
- Run the pipeline and confirm the image build completes successfully
- Observe the build log shows the pinned version argument supplied by the pipeline, matching the orchestration default
Prerequisite: Step 1
Developer Notes:
- Reuse the same version-parameter entry point the local orchestration uses, so pipeline and local builds stay identical
- The build validates the recipe only — nothing is published or pushed anywhere

Step 7. Finalize the pipeline configuration to repository conventions with validation-only scope
Must Support:
- Workflow configuration files committed in the repository's conventional location
- Conformance with the repository's documented CI/CD conventions reference
- The pipeline contains build and validation jobs only — no deployment actions (deployment is a later story)
Manual Verification:
- Review the committed configuration against the conventions reference and confirm structure and naming match
- Confirm the pipeline defines no deployment job and only the checks from Steps 2–6
Prerequisite: Steps 2 through 6
Developer Notes:
- Treat the conventions reference as the review checklist for the final configuration
- Keep job names descriptive of their check so failures are self-explanatory
