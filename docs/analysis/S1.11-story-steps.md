Story S1.11 Implementation Steps:

Step 1. Pin the target platform and runtime versions for this upgrade step
Must Support:
- The exact target version from the 5.x line is researched and recorded as this step's pin
- The runtime version required by the pinned target is identified and recorded
- The version-pinning documentation records both pins for this step, replacing the previous step's pins
Manual Verification:
- The pinning documentation shows the exact target and runtime versions for this step (no "latest stable" wording)
- The recorded runtime version matches the one the pinned target requires
Prerequisite: Story S1.10 completed (platform running the pinned 4.x)
Developer Notes:
- Consult the platform's official release information to confirm the target version and its required runtime version before pinning
- Record the pair together so each upgrade step's pins stay traceable across the sequence

Step 2. Update the dependency declaration and lock file to the pinned target
Must Support:
- The dependency declaration names the pinned target version
- The lock file is updated to match the declaration
- The declared runtime platform version matches the pinned runtime
Manual Verification:
- The dependency files show the pinned target and runtime versions
- A dependency install from the lock file completes successfully
Prerequisite: Step 1
Developer Notes:
- Keep the updated lock file committed so the pinned pair is reproducible from a fresh checkout

Step 3. Rebuild the runtime image from the pinned per-step base image
Must Support:
- The runtime image builds from the base image pinned for this step
- The rebuilt image reports the pinned runtime version
Manual Verification:
- The image build completes without errors
- The running container reports the pinned runtime version
Prerequisite: Steps 1 and 2
Developer Notes:
- The runtime version changes at this step; rebuild the runtime image so local and production run the same runtime
- Clear any cached artifacts from the previous runtime so stale caches cannot mask upgrade issues

Step 4. Reuse the verified database copy from the previous upgrade steps
Must Support:
- The database copy restored in the previous upgrade steps is present and reachable
- The copy is at the previous target's schema (upgraded through the 4.x step)
- The local site loads against the copy at the previous version before upgrading
- No fresh restore from the production database is performed at this step
Manual Verification:
- The local site loads and an admin can log in against the existing copy before the upgrade
- The copy's continuity from the previous upgrade step is confirmed (no new restore was needed)
Prerequisite: Story S1.10 completed (the verified copy exists at the 4.x schema)
Developer Notes:
- Per the agreed reuse approach, intermediate upgrade steps reuse the same verified copy; the fresh, updated restore from the live production database (still running Elgg 2.3.17) is deferred to the final upgrade step (S1.13)
- The reused copy traces to the production snapshot restored when the upgrade sequence started

Step 5. Execute the official upgrade procedure against the reused copy
Must Support:
- The platform's official upgrade procedure runs against the reused copy
- The upgrade completes without fatal errors
- Any post-upgrade maintenance steps the platform requires are completed
Manual Verification:
- The upgrade procedure reports successful completion
- The upgrade output shows no fatal errors
Prerequisite: Steps 3 and 4
Developer Notes:
- Run the upgrade under the runtime pinned in Step 1 so the exact (target, runtime) pair that will ship is exercised
- Capture the upgrade output for the runbook entry

Step 6. Verify the site is functional post-upgrade
Must Support:
- An administrator can log in after the upgrade
- Core pages browse without fatal errors
- The site reports the upgraded target version
Manual Verification:
- Log in as an administrator and browse the core pages; observe no fatal errors
- The platform's version information shows the pinned 5.x target
Prerequisite: Step 5
Developer Notes:
- Walk the core pages as a signed-in administrator rather than checking only the front page

Step 7. Verify scheduled maintenance tasks execute after the upgrade
Must Support:
- The scheduled intervals trigger the platform's maintenance routines through the same entry point web requests use
- A triggered run completes without errors under the new runtime version
Manual Verification:
- Trigger or wait for a scheduled interval and observe its completion in the logs
- Observe no errors for the scheduled run after the upgrade
Prerequisite: Step 6
Developer Notes:
- The runtime version change is the risk point for scheduled tasks; verify at least one triggered run under the new runtime

Step 8. Take and verify the pre-upgrade production backup
Must Support:
- A production database backup is taken before any production change at this upgrade point
- The backup is verified usable before proceeding
Manual Verification:
- The backup artifact exists with the expected size and completion marker
- A verification check (restore test or integrity check) confirms the backup is usable
Prerequisite: Step 6
Developer Notes:
- Never deploy an upgrade to production without a verified backup
- Record the backup artifact location for the runbook entry

Step 9. Deploy the upgraded stack to production
Must Support:
- The production stack is deployed at the pinned (target, runtime) pair
- The production database is upgraded in sync at this upgrade point
Manual Verification:
- The production site reports the pinned target version
- The deployment record shows this upgrade point's deployment
Prerequisite: Steps 7 and 8
Developer Notes:
- Deploy the same pinned pair validated locally; no floating versions at the deploy step

Step 10. Verify production is functional post-upgrade
Must Support:
- An administrator can log in to the production site
- Core pages browse without fatal errors in production
Manual Verification:
- Log in to production and browse the core pages; observe no fatal errors
Prerequisite: Step 9
Developer Notes:
- Repeat the core-page walk in production, not just a homepage check

Step 11. Update the upgrade runbook
Must Support:
- The runbook records this step's executed procedure (backup → upgrade → deploy → verify)
- Step-specific deviations (runtime version change, image rebuild, database-copy reuse) are documented for reuse
Manual Verification:
- The runbook contains this step's entry and a reader can follow it end-to-end
Prerequisite: Step 10
Developer Notes:
- The runbook entry is the reusable template for the remaining upgrade steps; note any deviations observed
