Story S1.12 Implementation Steps:

Step 1. Identify the exact target versions for the fourth major-version hop
Must Support:
- Resolution of the newest stable release of the next major core version from official release information
- Determination of the exact runtime version that release requires
- A recorded decision on whether the currently pinned runtime satisfies the new requirement
Manual Verification:
- The recorded target pair is exact (no floating constraints) and cites the official source and query date
- Any incompatibility between the new core and the current runtime is identified before anything is declared
Prerequisite: The currently pinned core and runtime pair is documented as the active pin
Developer Notes:
- Record the resolution source and date so later steps can audit the decision
- If the current runtime does not satisfy the new requirement, plan the runtime move as its own step

Step 2. Declare the pinned pair across the project's version surfaces
Must Support:
- Exact declarations of the new core and runtime versions in the dependency manifest and lock file
- Baseline documentation updated so the new pair is the active pin, with the previous pin preserved as the resolution record
- Pin-consistency checks updated to expect the new pair
Manual Verification:
- The manifest, lock file, and baseline documentation all agree on the same exact pair
- Any pin-consistency checks run green against the new pair
Prerequisite: Step 1

Step 3. Rebuild the runtime environment when the runtime pin moves
Must Support:
- The runtime environment rebuilt on the required base version whenever the new pin demands a different runtime
- The dependency tree installed and synced inside the rebuilt environment
Manual Verification:
- The running environment reports the new runtime version
- An install from the lock file completes without errors inside the rebuilt environment
Prerequisite: Step 2

Step 4. Execute the official upgrade against the copied database
Must Support:
- The verified local copy of the production database upgraded with the official upgrade tooling
- Any failed or skipped migration remediated, with each remediation recorded
Manual Verification:
- The upgrade tooling completes without fatal errors
- The upgraded database reports the expected version markers and an empty pending-migrations list
Prerequisite: Steps 2 and 3

Step 5. Verify the upgraded site locally
Must Support:
- Admin login and representative core pages functional on the upgraded copy
- A clean application-log scan across a browsing window
Manual Verification:
- Admin login succeeds and representative pages render correctly
- The log scan shows no fatal or critical entries during the session
Prerequisite: Step 4

Step 6. Verify scheduled tasks and the guard suite on the upgraded copy
Must Support:
- Every scheduled interval executing successfully under the new version
- The automated guard suite running green against the new pin
Manual Verification:
- Scheduled-task logs show each interval completing without errors
- The guard suite reports all tests passing
Prerequisite: Step 5

Step 7. Take and verify the pre-upgrade production backup
Must Support:
- A fresh production database backup taken before any production change at this hop
- The backup's restorability proven into a scratch database
Manual Verification:
- The backup file exists with its recorded size and restores cleanly into a scratch database with the expected table count
Prerequisite: Step 5 (local readiness gate; production remains untouched until Step 8)

Step 8. Deploy the upgraded platform to production in sync
Must Support:
- Production running the new pinned pair at this upgrade point
- The production database upgraded with the official tooling, in sync with the deployed code
- Recovery from any interrupted pass via the verified backup
Manual Verification:
- The production admin area reports the new version and representative pages render
- File handling and outgoing email work on production
- The unchanged pins (database, scheduled-task base) are cross-checked
Prerequisite: Steps 6 and 7

Step 9. Record the hop in the upgrade runbook
Must Support:
- The runbook extended with this hop's procedure, blockers and their remediations, and the verification figures
- Newly discovered operational gotchas recorded for the next hop
Manual Verification:
- A reader can reproduce this hop from the runbook section alone
Prerequisite: Step 8
