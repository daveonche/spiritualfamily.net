Story S1.4 Implementation Steps:

Step 1. Produce the dropped-plugins disposition list
Must Support:
- Identify every third-party and legacy plugin present in the codebase, including inactive ones
- Record, for each plugin, whether an upgraded replacement is provisioned through the project's dependency mechanism or it must be installed manually in a later sprint
- Record explicit deferrals for plugins intentionally kept until later sprint work
- Cross-check the list against the project's recorded drop and replacement decisions before finalizing
Manual Verification:
- The committed list names every plugin being dropped with exactly one disposition each
- Every plugin named in the project's recorded decisions appears on the list with a matching disposition
Prerequisite: None
Developer Notes:
- Build the list before removing anything so the removals execute a recorded plan
- Presence in the codebase is what matters, not activation status
- Keep the list format simple enough to scan manually during later verification

Step 2. Drop the legacy theme stack
Must Support:
- Remove the legacy theme plugins identified in the disposition list
- The site renders on the platform's default bundled views after removal
Manual Verification:
- The legacy theme plugins no longer appear in the codebase
- The site loads and pages render using default bundled styling
Prerequisite: Step 1 (the disposition list records the theme plugins)
Developer Notes:
- Dropping the theme before other plugins surfaces styling-dependent breakage early
- Expect visual differences; visual parity is deferred to the new theme arriving in a later story

Step 3. Drop the legacy core plugins
Must Support:
- Remove the core plugins named in the disposition list that are not bundled in the target platform version
- Record, for each dropped plugin, whether its maintenance duty is covered by a surviving mechanism or explicitly deferred
Manual Verification:
- None of the listed core plugins appears in the codebase
- The site loads without errors referencing the removed plugins
Prerequisite: Step 1
Developer Notes:
- Some duties may be covered by surviving mechanisms or scheduled work; record the coverage rather than assuming it
- Duties such as outgoing-email validation must remain functional after removal

Step 4. Drop the remaining third-party plugins
Must Support:
- Remove every remaining third-party plugin named in the disposition list
- No third-party plugin code remains anywhere in the codebase
Manual Verification:
- A search of the codebase finds no third-party plugin directories or references
- The disposition list and the codebase agree: every listed plugin is gone
Prerequisite: Steps 1-3
Developer Notes:
- Remove in one pass and verify once, rather than piecemeal, so the end state is unambiguous
- Plugins slated for manual reinstallation later are still removed now; the disposition list records their return path

Step 5. Verify the site functions on core and bundled views
Must Support:
- The site loads, an administrator can log in, and core pages render after all removals
- No errors arise from missing plugin dependencies
Manual Verification:
- Log in as an administrator and browse the main site areas without errors
- Confirm the logs contain no references to missing or deactivated plugins
Prerequisite: Steps 2-4
Developer Notes:
- This verification closes the story; any failure traces back to a specific removal step
