# S1.3 Story Steps — Elgg 2.3 Installation and Configuration in Compose

Source story: `docs/sprints/sprint_1_stories.md` → Story S1.3 (Dependencies: S1.2)

Dependency context: no dependency report was generated for S1.3 — all functionality is covered by the approved S1.1/S1.2 set (composer-managed pinned Elgg core, Docker Compose stack, MariaDB client tooling). If any step uncovers functionality not covered by existing dependencies, implementation stops and invokes `$code-dependency-management`.

---

## Step 1: Complete env-driven `settings.php`

Must Support:

- Every environment-specific Elgg setting (DB host, DB name, DB user, DB password, data directory path, cache directory path, and any optional services enabled) is injected via `getenv()` in `src/elgg-config/settings.php`
- The committed `.env.example` template documents every required variable with placeholder values only; secrets are excluded

Developer Notes:

- Extend the env-injection coverage proven in S1.2 (`src/tests/ComposeEnvInjectionTest.php`) to the full settings surface
- The site URL is not a `settings.php` setting in Elgg 2.3: it is stored on the site entity in the database (written at install time) and `$CONFIG->wwwroot` is overwritten from the DB on every boot — the URL is therefore taken from the environment (`APP_HOST`/`APP_HOST_PORT`) by the install procedure in Step 3
- Never commit real credentials

Manual Verification:

- Inspect `settings.php`: no hard-coded environment-specific values remain
- Compare `.env.example` variables against every `getenv()` call in `settings.php`

## Step 2: Provision the Elgg data directory on its persistent volume

Must Support:

- The Elgg data directory is provisioned on its persistent named volume with correct ownership/permissions for the web container user

Developer Notes:

- Reuse the named volumes established in S1.2; add a volume definition only if the data path is not yet covered

Manual Verification:

- Create a file in the data directory from inside the web container, restart the stack, and confirm the file survives

## Step 3: Run the Elgg 2.3 installer against the MySQL service

Must Support:

- The pinned Elgg 2.3 installs against the MySQL service and the schema installs cleanly
- The install is reproducible: committed CLI/provisioning commands preferred; documented manual steps acceptable where 2.3-era tooling requires them

Developer Notes:

- Confirm the pinned Elgg 2.3 + PHP pair (resolving the S1.1 pin flags) before installing
- Prefer `elgg-cli`/committed provisioning commands over browser-only installation

Manual Verification:

- From a fresh database and empty data directory, the installer completes without schema errors and the site responds

## Step 4: Admin login verification

Must Support:

- The site loads and an admin can log in

Developer Notes:

- Capture the verification steps in the install procedure documentation (feeds Step 6)

Manual Verification:

- Browse to the site, log in as the created admin, and reach the admin dashboard

## Step 5: Production dump restore (migration-readiness check)

Must Support:

- A production database dump restores successfully into the containerized MariaDB 10.11.18 service

Developer Notes:

- Use the production dump inventoried in S1.1 (see `docs/baseline/baseline.md`)
- Record the restore verification in `docs/baseline/baseline.md`

Manual Verification:

- Restore the dump into the db service and confirm table counts/content against the S1.1 inventory

## Step 6: Documentation update

Must Support:

- `docs/baseline/baseline.md` records the completed install/config: pinned Elgg 2.3 + PHP pair, data directory provisioning, and dump-restore verification
- The install procedure documentation reflects the completed install/config end to end

Developer Notes:

- Docs follow the repository's GitHub-Flavored Markdown conventions

Manual Verification:

- A new developer can reproduce the install from the documentation alone
