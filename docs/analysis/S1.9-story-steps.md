Story S1.9 Implementation Steps:

Step 1. Pin the exact target platform and runtime versions
Must Support:
- Selection of the exact target platform version, replacing the "latest stable" placeholder flagged in the story
- Selection of the exact runtime version required by that target platform version
- Recording of both pinned versions in the project's baseline/version documentation
- Declaration of the pinned pair in the build/version configuration so every environment resolves the same versions
Manual Verification:
- Open the baseline documentation and confirm the exact target and runtime versions are recorded, with no "latest stable" placeholders remaining
- Confirm the declared versions in the build configuration match the documented pins
Prerequisite: The cleaned baseline platform is deployed and reproducible (S1.6 complete)
Developer Notes:
- Resolve both pinning flags from the sprint story before any upgrade work begins
- Keep the documented pins and the configuration declarations in exact agreement

Step 2. Confirm the production site is installed and matches the local baseline
Must Support:
- Confirmation that production has completed the platform installation process and serves the working baseline site
- Completion of the installation on production at the baseline version when the confirmation finds it missing
- A parity comparison of production against the local baseline site: same reported version, administrator login, core pages rendering, no fatal errors
Manual Verification:
- Open production in a browser and confirm it shows the working baseline site, not an installation screen or error page
- Log in on production and browse the same representative core pages exercised on the local baseline; confirm both behave the same
- Confirm the version reported by production matches the version reported by the local baseline
Prerequisite: The cleaned baseline platform is deployed and reproducible (S1.6 complete)
Developer Notes:
- The upgrade must not proceed until production is a known-good, installed baseline; a site that never completed installation cannot be upgraded in sync with its database
- Record any remediation performed in the runbook so this confirmation is repeatable at the next upgrade point

Step 3. Rebuild the local environment at the pinned versions
Must Support:
- The local environment rebuilt from the version-parameterized configuration using the pinned pair
- The upgraded platform code served through the existing entry points
Manual Verification:
- Rebuild and start the local stack; confirm the running platform reports the pinned target version
- Confirm the site is reachable (full function is expected only after the upgrade step runs)
Prerequisite: Step 1
Developer Notes:
- The site may be partially non-functional between the code swap and the upgrade run; that is expected at this stage
- Reuse the same environment definitions that served the baseline so only the versions change

Step 4. Restore a copy of the production database into the local environment
Must Support:
- A fresh dump of the production database restored into the local database service
- The local site connected to the restored copy so the upgrade acts on production-shaped data
Manual Verification:
- Restore the dump and confirm table counts and content markers match the production source
- Confirm the local site connects to and reads from the restored copy
Prerequisite: Step 3
Developer Notes:
- Work only on the copy; the production database stays untouched until the deployment step
- Note the dump procedure and timing so the production backup step can reuse it

Step 5. Execute the official upgrade routine against the database copy
Must Support:
- The platform's official upgrade/migration routine executed end-to-end against the restored copy
- All pending migrations applied with no fatal errors
Manual Verification:
- Run the official upgrade routine and confirm it reports successful completion
- Confirm the log shows no fatal errors during the run
Prerequisite: Step 4
Developer Notes:
- Only the official mechanism satisfies this criterion; a hand-rolled migration would not
- Capture the exact commands and their output for the runbook step

Step 6. Verify the upgraded site locally
Must Support:
- Administrator login on the upgraded local site
- Core pages loading without errors
- No fatal errors in the platform log during browsing
Manual Verification:
- Log in as an administrator and confirm the dashboard loads
- Browse a representative set of core pages and confirm each renders
- Check the log for fatal errors after the browsing session
Prerequisite: Step 5
Developer Notes:
- Exercise the real pages by browsing the site, not just page-status checks — some failures only appear on specific pages
- Note any deprecation notices; they signal work needed at the next upgrade step

Step 7. Take and verify the pre-upgrade production database backup
Must Support:
- A full backup of the production database taken immediately before the production upgrade
- The backup verified as restorable before any production change
Manual Verification:
- Take the production backup and confirm it exists with the expected size
- Verify the backup restores successfully before proceeding
Prerequisite: Step 6
Developer Notes:
- Never deploy the upgrade to production without a verified backup (story rule)
- Retain the backup until the production upgrade is confirmed successful

Step 8. Deploy the upgraded stack to production with the database upgraded in sync
Must Support:
- Production deployment of the pinned upgraded stack via the established deployment procedure
- The production database upgraded at the same deployment point, so code and data move together
Manual Verification:
- Deploy and confirm production reports the pinned target platform version
- Confirm the production database upgrade completed as part of the deployment
Prerequisite: Step 7
Developer Notes:
- Code and database must move in one synchronized step; a mismatched state is the failure mode this criterion guards against
- Follow the deployment runbook's backup-then-upgrade-then-verify pattern

Step 9. Verify the production site post-upgrade
Must Support:
- Administrator login on production
- Core pages loading without errors
- No fatal errors in the production log
Manual Verification:
- Log in on the production site and confirm the dashboard loads
- Browse core pages and confirm each renders
- Check the production log for fatal errors
Prerequisite: Step 8
Developer Notes:
- Mirror the local verification so any local/production divergence surfaces immediately

Step 10. Document the executed upgrade steps in the runbook
Must Support:
- The runbook updated with the exact steps executed in this upgrade, in execution order
- The documentation written as a reusable template for future upgrade points
Manual Verification:
- Open the runbook and confirm the executed steps are recorded with their commands and verification outcomes
- Confirm a reader could repeat the procedure for the next upgrade point from the runbook alone
Prerequisite: Step 9
Developer Notes:
- Include the backup, upgrade, deploy, and verify sequence exactly as executed
- Include the production parity confirmation (Step 2) in the recorded sequence
- Note any deviations from the expected procedure and why they were needed
