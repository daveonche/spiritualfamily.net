# Story S1.2 Implementation Steps

Step 1. Enable version-parameterized web application image build
Must Support:

- Building the web application image with the runtime version supplied as a build-time input
- Every base image reference recorded at an exact pinned version for the current stage
- The built image serving all of the application's web entry points
Manual Verification:
- Build the web application image with the currently pinned runtime version and confirm the build completes without errors
- Open the site in a browser and confirm the application serves its front page from the built image
Prerequisite: The pinned core and runtime versions recorded in Story S1.1
Developer Notes:
- Keep the build recipe free of assumptions beyond the supplied version input
- Record base image versions where each journey stage can update them

Step 2. Enable version-pair-agnostic build inputs
Must Support:

- Build inputs that accept any combination of core version and runtime version
- Intermediate version combinations buildable from the same unedited files
Manual Verification:
- Rebuild the web application image with a different runtime version input and confirm the build succeeds
- Confirm no committed file needed editing to accept the alternate version pair
Prerequisite: Step 1
Developer Notes:
- This capability is what keeps every intermediate upgrade step buildable from one set of files

Step 3. Enable single-definition orchestration of web, database, and scheduled-task services
Must Support:

- One committed orchestration definition bringing up the web application, the database, and the scheduled-task service together
- The scheduled-task service running alongside the others on its configured schedule
- All services running in one shared, reproducible local environment
Manual Verification:
- Start the full environment from the committed definition and confirm the web, database, and scheduled-task services all come up
- Confirm the scheduled-task service executes on its configured schedule without errors
Prerequisite: Step 1
Developer Notes:
- Keep the definition usable for every stage of the journey; avoid stage-specific assumptions
- Keep schedules and commands in committed configuration

Step 4. Enable persistent storage for database and application data
Must Support:

- Dedicated persistent storage for the database data
- Dedicated persistent storage for the application data directory
- Both surviving service restarts and rebuilds
Manual Verification:
- Create data in the application, stop and restart the services, and confirm the data is still present
- Rebuild the services and confirm both the database data and the application data directory survive
Prerequisite: Step 3
Developer Notes:
- Provision storage so neither service loses state during routine restarts or rebuilds

Step 5. Enable exact database server version pinning
Must Support:

- An exact database server version replacing any floating "latest" reference
- A pinned version matching the production database server so local and production environments stay in sync
- A version choice that remains compatible across the journey or can be upgraded alongside it
- The pinned version recorded in project documentation
Manual Verification:
- Ask the running database for its server version and confirm it reports the pinned version
- Compare the running database's reported version against the production database's reported version and confirm they match
- Confirm the project documentation records the same pinned version
Prerequisite: Step 3
Developer Notes:
- Choose a version with a realistic path through the entire upgrade journey
- Record the pin alongside the version pair documented in Story S1.1

Step 6. Enable environment-variable injection of settings and secrets
Must Support:

- All environment-specific settings supplied as environment variables
- No credentials hard-coded in committed files
- A documented template listing every required variable without real secret values
Manual Verification:
- Bring up the environment using only the template plus locally supplied values and confirm the application runs
- Search committed files for hard-coded credentials and confirm none exist
Prerequisite: Step 3
Developer Notes:
- Keep the template complete so a fresh environment needs no undocumented values
- Real secrets never enter the repository

Step 7. Enable development-only mail capture — DROPPED
Step 8. Enable environment-driven mail routing in development — DROPPED

Steps 7 and 8 were dropped from Story S1.2: mail capture (formerly the MailHog service planned for `compose.dev.yml`) is now handled by a Docker Desktop extension as external developer tooling, outside the committed orchestration. Consequences:

- No mail-capture service exists in any committed definition, so the former "production excludes the capture service" requirement is satisfied trivially.
- No mail-routing environment variables are defined in `.env.example`.
- No automated tests are required for these steps; if the decision is reversed, resume with `$testing-unit-test S1.2 7`.
