Story S1.1 Implementation Steps:

Step 1. Enable identification and pinning of the exact legacy platform core version
Must Support:
- Determination of the exact core version currently in use, taken from the existing codebase
- A single recorded, pinned version value that all later steps reference
- The pinned version recorded in project documentation
Manual Verification:
- Open the project documentation and confirm the exact core version is recorded there
- Cross-check the recorded value against the version reported by the running legacy site's administration area
Prerequisite: None
Developer Notes:
- Record the version in a dedicated documentation location agreed by the team
- The recorded value becomes the ground-zero reference for every later upgrade step

Step 2. Enable pinning of the required runtime language version
Must Support:
- Determination of the runtime language version required by the pinned core version
- A single recorded, pinned runtime version value documented alongside the core version
Manual Verification:
- Confirm the documentation lists the runtime version directly next to the core version
- Confirm the recorded runtime version matches the one the production environment currently runs
Prerequisite: Step 1
Developer Notes:
- Note any constraints the pinned core version places on acceptable runtime versions
- Keep both pinned values visible together so future steps can cite them as a pair

Step 3. Enable declaration of pinned versions in the dependency manifest with a committed lock file
Must Support:
- A dependency manifest declaring the pinned core version and the pinned runtime platform version
- A lock file generated from that manifest and committed to the repository
- Ongoing consistency between the manifest and the lock file
Manual Verification:
- Open the manifest and confirm the exact pinned versions appear with no open-ended ranges
- Confirm the lock file is present in the repository and corresponds to the manifest
Prerequisite: Steps 1 and 2
Developer Notes:
- Keep the manifest and lock file under version control together so installs stay reproducible
- Avoid loose version ranges; exact values keep every environment identical

Step 4. Enable inventory of the production database and data directory
Must Support:
- A capture of the production database size, active plugin set, and key settings in storable form
- A measurement and content summary of the data directory
- Stored inventory results serving as the migration starting point
Manual Verification:
- Open the inventory record and confirm database size, plugin list, and settings are all present
- Confirm the data directory summary reflects the content volume actually stored in production
Prerequisite: Step 1
Developer Notes:
- Store the inventory where the team can reach it during later upgrade steps
- Treat the inventory as read-only reference data; never modify production while capturing it

Step 5. Enable verification that the baseline builds and runs from a fresh checkout
Must Support:
- A repeatable procedure that takes a clean checkout to a running baseline
- Confirmation that the site loads and an administrator can log in from that fresh checkout
Manual Verification:
- Start from a clean checkout, follow the documented procedure, and confirm the site loads
- Log in as an administrator and confirm the administration area is reachable and functional
Prerequisite: Steps 3 and 4
Developer Notes:
- Document the procedure so any team member can repeat it without help
- Note any manual steps that could not yet be automated
