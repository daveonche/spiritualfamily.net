Story S1.6 Implementation Steps:

Step 1. Enable the production application definition from the repository's Compose files
Must Support:
- A production application created in the deployment platform from the repository's Compose files as the single source of truth
- The app, dbm, and cron services all defined and startable as one stack
- The pma service kept out of the production stack (development-only database administration)
Manual Verification:
- Open the deployment platform and confirm one application listing the app, dbm, and cron services
- Confirm the pma service is not part of the production stack
Prerequisite: Stories S1.4 and S1.5 complete (plugin-clean baseline with green CI)
Developer Notes:
- Derive the definition from the committed Compose files rather than re-creating services by hand, so the repository remains the single source of truth
- Focus on the operator being able to see and start the full service trio as one unit

Step 2. Enable fully pinned, repository-reproducible version references
Must Support:
- Every image/version reference in the production definition resolves to an exact pinned version
- Deployed versions match the pins recorded in the repository's baseline documentation
- No floating tags (latest-style or major-only) anywhere in the deployed definition
Manual Verification:
- Inspect each service's version reference in the platform and confirm it is exact
- Cross-check the deployed versions against the recorded baseline pins
Prerequisite: Step 1
Developer Notes:
- Treat any tag that can move over time as floating, even if it currently resolves to the desired version
- The operator should be able to reproduce the deployment from the repository alone

Step 3. Enable secret injection through the deployment platform's environment settings
Must Support:
- All secrets supplied exclusively via the platform's environment variable settings
- Every variable required by the committed template is accounted for in the platform settings
- The repository contains only documented templates with no real secret values
Manual Verification:
- Confirm each required secret is set in the platform's environment settings
- Search the repository for real secret values and confirm none are committed
Prerequisite: Step 1
Developer Notes:
- The committed template documents every required variable; the platform holds the real values
- Never paste real credentials into any committed file

Step 4. Enable HTTPS entry routing to the app service
Must Support:
- Inbound HTTPS traffic routed to the app service
- TLS termination at the platform's entry point in front of the app container
- A valid certificate served for the production domain
Manual Verification:
- Load the site over HTTPS in a browser and confirm a valid certificate with no warnings
- Confirm the production domain resolves to the deployed stack
Prerequisite: Step 1
Developer Notes:
- Entry routing terminates before the app container; the app receives the forwarded request
- Focus on the user reaching the site securely over the production domain

Step 5. Enable production email over real SMTP with dev-only overrides excluded
Must Support:
- The production deployment includes no dev-only Compose override files
- The outgoing-mail relay variables overridden from their development defaults to the production relay via platform environment settings
- A triggered email is delivered through the real relay
Manual Verification:
- Confirm no dev-only override configuration is active in the production deployment
- Trigger an email (e.g., a user validation message) and confirm it arrives via the real SMTP relay
Prerequisite: Step 3
Developer Notes:
- The development email-capture defaults baked into the Compose environment must be replaced by production values at the platform level
- Verify delivery end-to-end rather than assuming the defaults are absent

Step 6. Enable the deploy runbook with the pre-deploy database backup
Must Support:
- A written deploy runbook covering the full deployment sequence
- A database backup step executed before any production data operation
- The runbook stored in the repository documentation
Manual Verification:
- Follow the runbook's backup step and confirm a restorable backup is produced
- Confirm the runbook file is committed
Prerequisite: Step 1
Developer Notes:
- The backup step is documented here and automated in later work
- The runbook should be reusable for future deployment points

Step 7. Enable production database migration into the dbm service with baseline sync verification
Must Support:
- The production database restored into the deployed dbm service
- A verification comparing the migrated database against the baseline inventory/dump
- The operator able to confirm the migrated data matches the recorded baseline starting point
Manual Verification:
- Restore the production dump into the deployed dbm service following the runbook
- Compare table contents/counts and key settings against the baseline inventory and confirm they match
Prerequisite: Step 6 (backup verified before touching production data)
Developer Notes:
- Take the backup before the migration; restore only after the backup is verified
- The comparison proves the containerized stack faithfully hosts the production data

Step 8. Enable clean re-deploy reproducibility of the identical stack
Must Support:
- The stack torn down and re-deployed from the repository alone
- Versions and configuration after re-deploy identical to the prior deployment
- One clean re-deploy performed and compared
Manual Verification:
- Perform one clean re-deploy following the runbook
- Compare deployed versions, services, and configuration against the prior deployment and confirm they are identical
Prerequisite: Steps 2, 5, and 7 (pinned versions, production email, migrated data)
Developer Notes:
- The re-deploy must rely on nothing that exists only on the deployment host
- This single verification proves the deployment is reproducible before any upgrade work begins
