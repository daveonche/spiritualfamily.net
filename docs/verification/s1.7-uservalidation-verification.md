# S1.7 Step 4 — Account-Validation Notification Task Verification Record

Repeatable end-to-end verification of the account-validation notification
task on the pinned Elgg 2.3.17 baseline: the bundled `uservalidationbyemail`
plugin's validation email, seeded so the notification effect is observable.
Re-run this procedure after every upgrade step in the sequence and fill in
the Observed outcome section.

## Trigger-path finding (pinned 2.3.17)

The plugin registers no cron handler. `uservalidationbyemail_init()` in the
plugin's `start.php` hooks registration, post-registration forwarding, PAM
authentication, login, admin validation, walled-garden public pages, and
admin actions — never the `cron` event. The validation email is sent by
`uservalidationbyemail_request_validation()` (in the plugin's
`lib/functions.php`, via `notify_user()`) from two trigger paths:

- Registration — the `register`/`user` plugin hook handler
  `uservalidationbyemail_disable_new_user` marks the account unvalidated,
  disables it, and requests the validation email.
- Failed login — the `login:before`/`user` event handler
  `uservalidationbyemail_check_manual_login` re-sends the validation email
  when an unvalidated account attempts to log in, and blocks the login.

There are no cron-driven expiry notifications or reminders in this core
version. This step therefore verifies the notification work end-to-end
through the plugin's real trigger path; the per-upgrade duty below re-checks
whether a later core version adds cron-driven reminders.

## Preconditions

- The `uservalidationbyemail` plugin is active (Administer → Plugins).
- Outgoing mail is captured by the development environment (Docker Desktop
  MailHog extension — inspect the app container's Mail tab).
- An admin account exists for the admin-panel check.

## Seed a pending account

Register a fresh account through the site's registration form with the
plugin active, and note the email address used. The plugin's registration
hook disables the account, marks it unvalidated, and sends the validation
email — the first observable notification.

Confirm the pending state: the account appears under Administer → Users →
Unvalidated.

## Observe the notification effect

- Open the mail capture (Docker Desktop MailHog extension, app container's
  Mail tab) and locate the message addressed to the pending account's email
  address.
- Confirm the subject and body match the plugin's `email:validate:subject`
  and `email:validate:body` language keys.
- Confirm the body carries the signed validation link:
  `uservalidationbyemail/confirm?u=<guid>`, signed via
  `elgg_http_get_signed_url()` (see `lib/functions.php`).
- On a re-run without a fresh registration, trigger the resend path instead:
  attempt to log in with the pending account's credentials; the plugin
  re-sends the validation email and blocks the login with the
  `uservalidationbyemail:login:fail` message.

## Per-upgrade duty

At each upgrade step in the sequence (S1.9–S1.13), before re-running this
verification:

- Re-check the upgraded core's `uservalidationbyemail` for cron-driven
  notification work (expiry notifications, reminders). If the plugin gains a
  cron handler, add its interval to the committed `crontab` (following the
  crontab's per-upgrade duty), move this verification to the scheduled run,
  and update this record together with the Step 4 text in
  `docs/analysis/S1.7-story-steps.md`.
- Re-verify the notification effect through whichever trigger path the
  upgraded core provides, and re-fill the Observed outcome section.
