# S1.7 Step 4 — Account-Validation Notification Task Verification Record

Repeatable end-to-end verification of the account-validation notification
task: the bundled `uservalidationbyemail` plugin's validation email,
seeded so the notification effect is observable. First recorded on the
pinned Elgg 2.3.17 baseline (2026-10-25); re-verified at Elgg 4.3.10
(2026-11-15, Story S1.10 Step 7). Re-run this procedure after every
upgrade step in the sequence and fill in the Observed outcome section.

## Trigger-path finding (pinned 2.3.17; re-checked at 4.3.10)

The plugin registers no cron handler — re-confirmed at Elgg 4.3.10 (the
plugin's `elgg-plugin.php` registers menus, a controller, and the
registration/login handlers below; no `cron` hook). On 2.3.17,
`uservalidationbyemail_init()` in the plugin's `start.php` hooked
registration, post-registration forwarding, PAM authentication, login,
admin validation, walled-garden public pages, and admin actions — never
the `cron` event. The validation email is sent by
`uservalidationbyemail_request_validation()` (in the plugin's
`lib/functions.php`, via `notify_user()` — unchanged in 4.3.10) from two
trigger paths:

- Registration — on 2.3.17 the `register`/`user` plugin hook handler
  `uservalidationbyemail_disable_new_user`; on 4.3.10 the same
  registration hook is served by the class-based handler
  `Elgg\UserValidationByEmail\User::disableUserOnRegistration` (the
  3.x→4.0 bootstrapping move from `start.php` functions to
  `elgg-plugin.php` registrations). It marks the account unvalidated,
  disables it, and requests the validation email.
- Failed login — on 2.3.17 the `login:before`/`user` event handler
  `uservalidationbyemail_check_manual_login`; on 4.3.10 the class-based
  `Elgg\UserValidationByEmail\User::preventLogin`. It re-sends the
  validation email when an unvalidated account attempts to log in, and
  blocks the login.

There are no cron-driven expiry notifications or reminders in either core
version. This step therefore verifies the notification work end-to-end
through the plugin's real trigger path; the per-upgrade duty below re-checks
whether a later core version adds cron-driven reminders.

## Preconditions

- The `uservalidationbyemail` plugin is active (Administer → Plugins).
- Outgoing mail is captured by the development environment (Docker Desktop
  MailHog extension — inspect the app container's Mail tab).
- An admin account exists for the admin-panel check.

## Seed a pending account

Register a fresh account through the site's registration form with the
plugin active, and note the email address used. The plugin's registration
hook disables the account, marks it unvalidated, and sends the validation
email — the first observable notification.

Confirm the pending state: the account appears under Administer → Users →
Unvalidated.

## Observe the notification effect

- Open the mail capture (Docker Desktop MailHog extension, app container's
  Mail tab) and locate the message addressed to the pending account's email
  address.
- Confirm the subject and body match the plugin's `email:validate:subject`
  and `email:validate:body` language keys.
- Confirm the body carries the signed validation link:
  `uservalidationbyemail/confirm?u=<guid>`, signed via
  `elgg_http_get_signed_url()` (see `lib/functions.php`).
- On a re-run without a fresh registration, trigger the resend path instead:
  attempt to log in with the pending account's credentials; the plugin
  re-sends the validation email and blocks the login with the
  `uservalidationbyemail:login:fail` message.

## Per-upgrade duty

At each upgrade step in the sequence (S1.9–S1.13), before re-running this
verification:

- Re-check the upgraded core's `uservalidationbyemail` for cron-driven
  notification work (expiry notifications, reminders). If the plugin gains a
  cron handler, add its interval to the committed `crontab` (following the
  crontab's per-upgrade duty), move this verification to the scheduled run,
  and update this record together with the Step 4 text in
  `docs/analysis/S1.7-story-steps.md`.
- Re-verify the notification effect through whichever trigger path the
  upgraded core provides, and re-fill the Observed outcome section.

  in the captured outgoing mail — Docker Desktop MailHog extension, app

  (`uservalidationbyemail/confirm?u=...`)
- Notes: the first registration attempt (19:24:40) fataled with
  `Unable to send mail: Unknown error` — the Laminas Mail sendmail
  transport failing inside `/action/register`; no user entity was
  created (the fatal fired before insertion). Diagnosis: the msmtp
  wrapper → relay chain (`host.docker.internal:1025`, the Docker Desktop
  MailHog extension) was probed directly and delivered, so the failure
  was transient relay unavailability at the moment of registration, not
  a 3→4 regression — the immediate re-run succeeded end-to-end through
  the full PHP mail path (Laminas SendmailTransport → `mail()` → msmtp
  wrapper → relay → MailHog). The trigger path remains registration (no
  cron handler at 4.3.10 — finding above re-confirmed); the failed-login
  resend path was not exercised in this run.
