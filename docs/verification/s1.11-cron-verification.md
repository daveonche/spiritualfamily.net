# S1.11 Step 7 — Scheduled-Task Verification Record (Elgg 5.1.12 / PHP 8.2.21)

Repeatable end-to-end verification of the cron-triggered scheduled tasks
after a runtime-version change: the cron container's intervals firing
through the app's web entry point under the newly pinned runtime, with the
maintenance routines completing error-free. First recorded at Story S1.11
Step 7 (2026-11-17) — the 4 → 5 hop that moved the runtime from PHP 7.4.27
to 8.2.21, the journey's first runtime change and this step's stated risk
point. Re-run this procedure after every later upgrade step that moves the
runtime (S1.12, S1.13) and fill in the Observed outcome section.

## Preconditions

- The merged dev stack is up (`docker compose -f compose.yml -f
  compose.dev.yml`): `app`, `dbm`, and `cron` all running.
- The app container reports the pinned runtime — PHP 8.2.21 at this
  recording (per `docs/baseline/baseline.md`, Pinned Versions).
- The committed crontab (`docker/cron/crontab`) is rendered into the cron
  container's spool at container start with the `APP_CRON_*` MAC tokens
  resolved; the tokens are secrets — never printed into transcripts,
  records, or command output.

## Task under verification

- The scheduled intervals trigger the platform's maintenance routines
  through the same entry point web requests use: the cron container's
  scheduled wget hit on `http://app:80/cron/<interval>?__elgg_mac=<token>`
  (the sanctioned entry point, unchanged across the upgrade sequence).
- A triggered run completes without errors under the new runtime version:
  the core's per-interval handlers execute, and the Elgg application log
  (`ELGG_LOG_FILE`) stays free of ERROR/CRITICAL/fatal/deprecation lines
  for the run window.

## Procedure

Wait-or-trigger: the minute interval fires on its own every 60 seconds, so
waiting past one tick observes the real scheduler end to end (the story's
Manual Verification allows "trigger or wait"). Name the capture files after
the executing step (here `s1.11-step7-*`; on a re-run, the new step's
prefix).

1. Confirm the runtime in the app container:

```bash
out=$(docker compose -f compose.yml -f compose.dev.yml exec -T app php -r 'echo PHP_VERSION;'); [ -n "$out" ] && printf '%s\n' "$out" || echo "EMPTY: no PHP version output (app container not running?)"
```

2. Wait past the next minute tick, then capture the cron log tail:

```bash
sleep 70; mkdir -p .log && docker compose -f compose.yml -f compose.dev.yml exec -T cron sh -c 'tail -n 30 /var/log/cron/app-cron.log' > .log/s1.11-step7-cron.log 2>&1 && echo OK || { echo FAILED; grep -nE "ERROR|E: |404" .log/s1.11-step7-cron.log | tail -n 20; }
```

3. Scan the Elgg application log over the run window:

```bash
mkdir -p .log && docker compose -f compose.yml -f compose.dev.yml exec -T app sh -c 'tail -n 300 "$ELGG_LOG_FILE" | grep -nE "ERROR|CRITICAL|Fatal|Deprecated" || echo NO-MATCHES: clean recent window' > .log/s1.11-step7-app-errors.log 2>&1 && echo OK || { echo FAILED; grep -nE "ERROR|E: |404" .log/s1.11-step7-app-errors.log | tail -n 20; }
```

Pass criteria: the captured cron log contains at least one
`Cron jobs for "<interval>" completed at …` line timestamped inside the
observation window with no wget error text, and the Elgg-log scan reports
`NO-MATCHES: clean recent window`.

## Recovery gotcha — stale `PHP_VERSION` shell export (instance 2)

The verification's first pass failed, and the failure is this record's
reason for existing. The stack check's `docker compose … up -d cron`
recreated the app container alongside starting cron; a stale
`PHP_VERSION=7.4` export in the command environment outranked the `.env`
and compose-default interpolation, so the recreate resolved the image tag
to the 7.4 line (`sfn/elgg_webserver:7.4-composer2`) against the Elgg
5.1.12 vendor tree, which requires PHP >= 8.2.0. Composer's
`platform_check.php` fataled every bootstrap — 500s on every request, the
cron ticks included (17 consecutive `wget: server returned error:
HTTP/1.1 500 Internal Server Error` lines after the last successful
14:48:01 run) — and the Elgg log stayed empty because the fatal precedes
logger initialization (the clean-scan step alone would therefore have
false-passed; the cron-log tail is what exposed it).

Remedy (the baseline doc's recorded gotcha, second instance): an explicit
`PHP_VERSION=8.2` assignment on the recreate command — the command
environment beats `.env` in Compose interpolation:

```bash
mkdir -p .log && PHP_VERSION=8.2 docker compose -f compose.yml -f compose.dev.yml up -d --force-recreate --no-deps app > .log/s1.11-step7-recreate.log 2>&1 && echo OK || { echo FAILED; grep -nE "ERROR|E: |404" .log/s1.11-step7-recreate.log | tail -n 20; }
```

First instance: the Step 3 image rebuild (recorded in
`docs/baseline/baseline.md`, Step 3 rebuild record). Runbook note for the
Step 11 entry: any Compose command that can recreate the app container
must carry the explicit `PHP_VERSION` pin.

## Host-header probe note

During recovery, a container-internal probe returned divergent codes by
Host header alone: `curl --header "Host: localhost" …` → `400`, while the
same request with the cron container's resolved `HOST` value → `200`. The
400 was probe-side (unknown host), not a runtime failure; the cron wget
sends the correct resolved Host header, which is why the scheduled ticks
are the authoritative check. When probing the app from inside a container,
send the site's `HOST` value, not `localhost`.
