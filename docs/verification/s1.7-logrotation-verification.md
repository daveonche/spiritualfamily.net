# S1.7 Step 5 — Scheduled-Task Output Log Rotation Verification Record

Repeatable end-to-end verification of the scheduled-task output log
rotation on the pinned Elgg 2.3.17 baseline: the cron container's daily
rotation of `/var/log/cron/app-cron.log`, seeded so the rotation and
retention effects are observable. Re-run this procedure after every
upgrade step in the sequence and fill in the Observed outcome section.

## Preconditions

- The cron container is up (`docker compose -f compose.yml -f
  compose.dev.yml up -d --build`).
- The rotation script is baked into the cron image at
  `/usr/local/bin/rotate-cron-log.sh` (`docker/cron/Dockerfile`).
- The active log `/var/log/cron/app-cron.log` sits on the `fs-cronlog`
  named volume, so archives survive container recreation.
- Retention window: `RETENTION_DAYS=7` in the rotation script.

## Task under verification

- Rotation entry: the committed crontab's daily line
  `30 0 * * * /usr/local/bin/rotate-cron-log.sh` — after the midnight
  Elgg jobs, so their output lands in the archived day.
- Mechanism: copy-truncate — the script copies the active log to a
  date-stamped archive, truncates the active log in place (the cron
  jobs hold it open in append mode, so their subsequent output is never
  lost), and gzips the archive.
- Retention: archives older than the window are removed automatically
  (`find "$LOG_DIR" -name 'app-cron.log.*.gz' -mtime +7 -delete`).
- Duty: the logging duty formerly covered by the dropped logrotate
  plugin (REQ-FR-PU-7), preserved by this configuration.

## Seed representative data

The active log must have content before a rotation: the minute job
writes a completion line every minute, so any running stack qualifies.
Confirm before rotating:

```bash
docker compose -f compose.yml -f compose.dev.yml exec cron sh -c 'ls -l /var/log/cron/ && tail -n 3 /var/log/cron/app-cron.log'
```

For the retention check, seed an archive backdated past the window:

```bash
docker compose -f compose.yml -f compose.dev.yml exec cron sh -c 'echo seed > /var/log/cron/app-cron.log.seed && gzip -f /var/log/cron/app-cron.log.seed && mv /var/log/cron/app-cron.log.seed.gz /var/log/cron/app-cron.log.20200101-000000.gz && touch -t 202001010000 /var/log/cron/app-cron.log.20200101-000000.gz'
```

## Run the rotation

Either wait for the daily 00:30 schedule or force-trigger the same
command the crontab schedules:

```bash
docker compose -f compose.yml -f compose.dev.yml exec cron /usr/local/bin/rotate-cron-log.sh
```

## Confirm the rotation effect

- Rotation point: `ls -l /var/log/cron/` shows a dated
  `app-cron.log.<timestamp>.gz` archive and the active log truncated.
- Continued writing: after the next minute tick, the active log carries
  fresh completion lines while the archive stays intact.
- Retention: after the rotation run, the backdated seeded archive is
  gone and the real archives remain.

## Observed outcome

- Date: 2026-10-26
- Rotation triggered: manual force-trigger of
  `/usr/local/bin/rotate-cron-log.sh` (the same command the crontab
  schedules daily at 00:30)
- Rotation point: the active log held 613 bytes of real cron output
  (minute, fiveminute, fifteenmin, hourly, halfhour completions,
  03:00–03:04); the run reported
  `rotated /var/log/cron/app-cron.log -> /var/log/cron/app-cron.log.20261026-030538.gz`
  and the active log was truncated to 0 bytes (archive 151 bytes)
- Continued writing: 70 seconds later the active log carried fresh
  minute completions (03:06:05, 03:07:03, 134 bytes) while the archive
  stayed intact
- Retention: the seeded archive `app-cron.log.20200101-000000.gz`
  (backdated with `touch -t 202001010000`) was deleted by the rerun;
  the real archives (`20261026-030538.gz`, `20261026-030922.gz`)
  remained
- Notes: the rerun also rotated the active log a second time
  (`20261026-030922.gz`) because the continued-writing check had
  refilled it — expected behaviour. Wiring is guarded by
  `src/tests/CronLogRotationTest.php`; this record by
  `src/tests/CronLogRotationVerificationTest.php`.
