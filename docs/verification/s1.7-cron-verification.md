# S1.7 Step 3 — Periodic Data-Cleanup Task Verification Record

Repeatable end-to-end verification of the scheduled data-cleanup task on
the pinned Elgg 2.3.17 baseline: the bundled `garbagecollector` plugin's
cron run, seeded so the cleanup effect is observable. Re-run this
procedure after every upgrade step in the sequence and fill in the
Observed outcome section.

## Preconditions

- The `garbagecollector` plugin is active (Administer → Plugins).
- Its `period` setting is known: `weekly`, `monthly`, or `yearly`; unset
  defaults to `monthly` (`garbagecollector_init()` in the plugin's
  `start.php`). The steps below say `<period>` for the configured value.
- Database access through the `dbm` container using the credentials from
  `.env` (never commit credentials); `<prefix>` is the `dbprefix` from
  `settings.php`.

## Task under verification

- Plugin: `garbagecollector` (bundled, vendored at
  `src/vendor/elgg/elgg/mod/garbagecollector/`)
- Registered interval: the plugin's `period` setting (default `monthly`)
- Cleanup work, triggered through the `gc`, `system` plugin hook:
  - orphaned `metastrings` rows — strings referenced by neither
    `metadata` nor `annotations`
  - orphaned entity stub rows — per-type `*_entity` tables vs. `entities`
  - `OPTIMIZE TABLE` on every database table
- Trigger path: the cron container's scheduled wget hit on
  `http://app:80/cron/<period>?__elgg_mac=<token>` (committed `crontab`;
  tokens rendered at container start from the `APP_CRON_*` environment
  variables into `/var/spool/cron/crontabs/root`)

## Seed representative data

Insert one deterministic orphaned metastring — referenced by nothing, so
the plugin's cleanup DELETE removes it:

```sql
INSERT INTO <prefix>metastrings (string) VALUES ('s1.7-orphan-seed');
```

Confirm the seed exists before the run:

```sql
SELECT id FROM <prefix>metastrings WHERE string = 's1.7-orphan-seed';
```

## Run the scheduled occurrence

Either wait for the configured interval or force-trigger the same
endpoint the crontab uses:

1. Read the rendered line from the installed spool file:

```bash
docker compose -f compose.yml -f compose.dev.yml exec cron cat /var/spool/cron/crontabs/root
```

2. Run the command portion of the `<period>` line (everything after the
   five schedule fields) verbatim inside the cron container.

## Observe start and completion

- `docker compose -f compose.yml -f compose.dev.yml logs cron` — the
  entrypoint runs `crond -f -d 8`, so each job execution is logged.
- The core persists per-period evidence as site private settings
  (`engine/lib/cron.php`): `cron_latest:<period>:ts` (last-run timestamp,
  written by `_elgg_cron_monitor`) and `cron_latest:<period>:msg` (the
  combined handler output, written by `_elgg_cron_page_handler`). Both
  are displayed in the admin panel under Statistics → Cron.
- Expected handler output keys (from the plugin's `start.php`):
  `garbagecollector` (start label), per-table `garbagecollector:optimize`
  with `garbagecollector:ok`/`garbagecollector:error`,
  `garbagecollector:gc:metastrings` with `:ok`/`:error`, and
  `garbagecollector:done`.

## Confirm the cleanup effect

After a completed run, re-run the seed check:

```sql
SELECT id FROM <prefix>metastrings WHERE string = 's1.7-orphan-seed';
```

An empty result confirms the seeded orphan was removed by the run. A
non-empty result after a completed run fails this verification.

## Observed outcome

- Date: 2026-10-25
- Period triggered: monthly (forced trigger through the same endpoint and
  MAC token the rendered crontab sends)
- Start/completion evidence: the cron endpoint response body showed the
  `GARBAGE COLLECTOR` start label, `Cleaning up unlinked metastrings: OK`,
  per-table `Optimizing … OK` lines, `DONE`, and the core completion line
  `Cron jobs for "monthly" completed at Sun, 25 Oct 2026 19:15:45 +0000`;
  the cron container log (`crond -f -d 8`) showed the scheduled wget
  executions
- Seed present before run (Y/N): Y (inserted as metastrings id 33)
- Seed removed after run (Y/N): Y (post-run SELECT returned an empty set)
- Notes: the metastrings cleanup handler reported OK and every table
  optimized OK. The handler's language keys render as their translated
  strings in the output (`garbagecollector:gc:metastrings` appears as
  "Cleaning up unlinked metastrings").
