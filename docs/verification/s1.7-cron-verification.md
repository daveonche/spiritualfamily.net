# S1.7 Step 3 — Periodic Data-Cleanup Task Verification Record

Repeatable end-to-end verification of the scheduled data-cleanup task:
the bundled `garbagecollector` plugin's cron run, seeded so the cleanup
effect is observable. First recorded on the pinned Elgg 2.3.17 baseline
(2026-10-25); re-verified and adapted at Elgg 4.3.10 (2026-11-15, Story
S1.10 Step 7). Re-run this procedure after every upgrade step in the
sequence and fill in the Observed outcome section.

## Preconditions

- The `garbagecollector` plugin is active (Administer → Plugins).
- Its `period` setting is known: `weekly`, `monthly`, or `yearly`; unset
  defaults to `monthly` — on 2.3.17 via `garbagecollector_init()` in the
  plugin's `start.php`, on 4.3.10 via the `elgg-plugin.php` default
  (same value). The steps below say `<period>` for the configured value.
- Database access through the `dbm` container using the credentials from
  `.env` (never commit credentials); `<prefix>` is the `dbprefix` from
  `settings.php`.

## Task under verification

- Plugin: `garbagecollector` (bundled, vendored at
  `src/vendor/elgg/elgg/mod/garbagecollector/`)
- Registered interval: the plugin's `period` setting (default `monthly`)
- Cleanup work, triggered through the `gc`, `system` plugin hook:
  - Elgg 2.3.17 (historical): orphaned `metastrings` rows — strings
    referenced by neither `metadata` nor `annotations`; orphaned entity
    stub rows — per-type `*_entity` tables vs. `entities`; and
    `OPTIMIZE TABLE` on every database table
  - Elgg 4.3.10 (current): the `OPTIMIZE TABLE` pass across every
    `{dbprefix}%` table (rotated system_log archive tables skipped),
    driven by `Elgg\GarbageCollector\CronRunner` — registered on the
    `cron` hook for all intervals in the plugin's `elgg-plugin.php`.
    The 2.3-era in-plugin metastrings cleanup is gone: the `metastrings`
    table was dropped in the 2.3→3.x schema consolidation, and no core
    or bundled handler responds to `gc, system` in 4.3.10
- Trigger path: the cron container's scheduled wget hit on
  `http://app:80/cron/<period>?__elgg_mac=<token>` (committed `crontab`;
  tokens rendered at container start from the `APP_CRON_*` environment
  variables into `/var/spool/cron/crontabs/root`) — unchanged across the
  upgrade sequence; re-confirmed as the sanctioned entry point at
  4.3.10 (`engine/routes.php` `/cron/{segments}` →
  `Elgg\Controllers\Cron`)

## Seed representative data

Elgg 2.3.17 (historical): insert one deterministic orphaned metastring —
referenced by nothing, so the plugin's cleanup DELETE removes it:

```sql
INSERT INTO <prefix>metastrings (string) VALUES ('s1.7-orphan-seed');
```

Confirm the seed exists before the run:

```sql
SELECT id FROM <prefix>metastrings WHERE string = 's1.7-orphan-seed';
```

Elgg 4.3.10 (current): the cleanup DELETE no longer exists — the run's
observable effect is the per-table `OPTIMIZE TABLE` pass, so seed a
probe table the pass must enumerate (dropped again after the run):

```sql
CREATE TABLE <prefix>s17_optimize_probe (id INT UNSIGNED NOT NULL AUTO_INCREMENT, PRIMARY KEY (id)) ENGINE=InnoDB;
```

Confirm the seed exists before the run:

```sql
SHOW TABLES LIKE '<prefix>s17_optimize_probe';
```

## Run the scheduled occurrence

Elgg 2.3.17: either wait for the configured interval or force-trigger
the same endpoint the crontab uses (the 2.3 endpoint ran the requested
interval unconditionally):

1. Read the rendered line from the installed spool file:

```bash
docker compose -f compose.yml -f compose.dev.yml exec cron cat /var/spool/cron/crontabs/root
```

2. Run the command portion of the `<period>` line (everything after the
   five schedule fields) verbatim inside the cron container.

Elgg 4.3.10: the endpoint is due-gated — `Elgg\Cron::run()` evaluates
each interval's cron schedule against the request time, so an
off-schedule hit on `/cron/monthly` returns HTTP 200 with an empty body
(observed 2026-11-15), and the core's `force` request parameter is
unusable over HTTP: the URL MAC signs the full query string
(`Elgg\Security\UrlSigner`), so `&force=1` cannot be appended to the
crontab's token. The adapted off-schedule path stays on the sanctioned
endpoint: temporarily move the plugin's `period` setting to `minute`
(always due; its spool token is valid), trigger `/cron/minute`, then
restore. The setting lives in `<prefix>private_settings` on the plugin
entity (the entity whose `title` metadata holds the plugin ID); because
a direct-SQL move bypasses Elgg's cache invalidation, clear the app
cache (`rm -rf "$WWW_CACHE"/*` in the app container) after both the move
and the restore.

## Observe start and completion

- `docker compose -f compose.yml -f compose.dev.yml logs cron` — the
  entrypoint runs `crond -f -d 8`, so each job execution is logged.
- Elgg 2.3.17 (historical): the core persisted per-period evidence as
  site private settings (`engine/lib/cron.php`):
  `cron_latest:<period>:ts` (last-run timestamp, written by
  `_elgg_cron_monitor`) and `cron_latest:<period>:msg` (the combined
  handler output, written by `_elgg_cron_page_handler`), displayed in
  the admin panel under Statistics → Cron. Expected handler output keys
  (from the plugin's `start.php`): `garbagecollector` (start label),
  per-table `garbagecollector:optimize` with
  `garbagecollector:ok`/`garbagecollector:error`,
  `garbagecollector:gc:metastrings` with `:ok`/`:error`, and
  `garbagecollector:done`.
- Elgg 4.3.10 (current): the private-settings mechanism is gone — no
  `cron_latest:*` rows are written, and `engine/lib/cron.php` no longer
  exists. Evidence channels: the HTTP response body itself (captured per
  scheduled run into `/var/log/cron/app-cron.log` by the crontab's
  wget), the core's per-interval filestore logs written by `Elgg\Cron`
  (`<interval>-output.log` / `<interval>-completion.log`), and the Elgg
  application log (`ELGG_LOG_FILE`). Expected output labels (from
  `Elgg\GarbageCollector\GarbageCollector`): `Garbage collector
  initialized: ok`, per-table `Optimizing <table>: ok. Completed:
  <datetime>`, and `Garbage collector done: ok`, followed by the core
  completion line `Cron jobs for "<interval>" completed at …`.

## Confirm the cleanup effect

Elgg 2.3.17 (historical): after a completed run, re-run the seed check:

```sql
SELECT id FROM <prefix>metastrings WHERE string = 's1.7-orphan-seed';
```

An empty result confirms the seeded orphan was removed by the run. A
non-empty result after a completed run fails this verification.

Elgg 4.3.10 (current): the run output must carry the probe table's own
optimize line — `Optimizing <prefix>s17_optimize_probe: ok. Completed:
<datetime>` — between the initialized and done labels. Afterwards drop
the probe table:

```sql
DROP TABLE <prefix>s17_optimize_probe;
```

## Observed outcome

- Date: 2026-11-15 (Elgg 4.3.10, Story S1.10 Step 7 re-verification)
- Period triggered: monthly by configuration — adapted off-schedule via
  the temporary `period=minute` move (due-gating; see Run the scheduled
  occurrence), triggered through `/cron/minute?__elgg_mac=<token>` with
  the spool's valid token
- Start/completion evidence: the response body (captured to
  `.log/minute-gc-run2.log`) showed `Garbage collector initialized: ok`,
  24 per-table `Optimizing …: ok` lines — including
  `Optimizing elggjr_s17_optimize_probe: ok. Completed:
  2026-11-15T19:14:04+00:00` (the seeded probe) —
  `Garbage collector done: ok`, and the core completion line
  `Cron jobs for "minute" completed at Sun, 15 Nov 2026 19:14:26 +0000`
- Seed present before run (Y/N): Y (probe table created and confirmed)
- Seed removed after run (Y/N): Y (probe table dropped; the temporary
  `period` row deleted — `period_rows_after` = 0 — and the app cache
  cleared after both)
- Notes: the first trigger attempt (before the cache clear) ran with no
  GC output — the direct-SQL setting move bypassed Elgg's cache
  invalidation, so the stale cached default (`monthly`) gated the
  handler; clearing `$WWW_CACHE` resolved it. An earlier off-schedule
  hit on `/cron/monthly` returned HTTP 200 with an empty body — the 4.x
  due-gating behaviour (the 2.3 endpoint ran unconditionally), recorded
  under Run the scheduled occurrence. Guarded by
  `src/tests/CronCleanupVerificationTest.php`.

- Date: 2026-10-25 (Elgg 2.3.17 baseline run)
- Period triggered: monthly (forced trigger through the same endpoint and
  MAC token the rendered crontab sends)
- Start/completion evidence: the cron endpoint response body showed the
  `GARBAGE COLLECTOR` start label, `Cleaning up unlinked metastrings: OK`,
  per-table `Optimizing … OK` lines, `DONE`, and the core completion line
  `Cron jobs for "monthly" completed at Sun, 25 Oct 2026 19:15:45 +0000`;
  the cron container log (`crond -f -d 8`) showed the scheduled wget
  executions
- Seed present before run (Y/N): Y (inserted as metastrings id 33)
- Seed removed after run (Y/N): Y (post-run SELECT returned an empty set)
- Notes: the metastrings cleanup handler reported OK and every table
  optimized OK. The handler's language keys render as their translated
  strings in the output (`garbagecollector:gc:metastrings` appears as
  "Cleaning up unlinked metastrings").
